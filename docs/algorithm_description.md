# Опис алгоритмів: паралельне множення матриць (блочний алгоритм)

## 1. Постановка задачі

Задано дві квадратні матриці A та B розміру n × n. Потрібно обчислити C = A · B, де

  C[i][j] = Σ<sub>l=0..n−1</sub> A[i][l] · B[l][j].

Кількість арифметичних операцій — 2n³ (n³ множень і n³ додавань), пам'ять — O(n²). Кожен елемент C обчислюється незалежно від інших, тому задача добре розпаралелюється, але на відміну від Монте-Карло потребує **передачі великих обсягів даних** (матриць) між вузлами, тому її масштабованість визначається співвідношенням «обчислення / комунікація».

### Блочна форма

Розіб'ємо матриці на плитки (блоки) розміром b × b. Тоді блок результату

  C<sub>IJ</sub> = Σ<sub>K</sub> A<sub>IK</sub> · B<sub>KJ</sub>,

тобто множення матриць зводиться до множення й додавання блоків. Блокова форма використовується на двох рівнях:

1. **Блоки для кеш-пам'яті** — всередині одного процесора (послідовне ядро, параметр `bs`);
2. **Блоки для розподілу між вузлами** — матриця C ділиться на блоки C<sub>IJ</sub>, кожен з яких обчислює окремий воркер ПАРКС.

## 2. Послідовні алгоритми (`SequentialMatMul`, `MmUtil`)

### 2.1 Наївний (`naive`)

```
для i = 0..n-1:
  для j = 0..n-1:
    s = 0
    для l = 0..n-1:  s += A[i][l] * B[l][j]
    C[i][j] = s
```
Матриця B читається **за стовпцями** (з кроком n елементів). Для великих n кожне звернення потрапляє в іншу кеш-лінію, і програма впирається в пам'ять, а не в обчислення.

### 2.2 Блоковий (`blocked`)

B зберігається транспонованою (Bt[j][l] = B[l][j]), тож і рядок A, і «стовпець» B лежать у пам'яті підряд.

```
для ii = 0, bs, 2bs, ... < n:            // плитка рядків A / C
  для jj = 0, bs, 2bs, ... < n:          // плитка стовпців B / C
    для kk = 0, bs, 2bs, ... < n:        // плитка за спільним індексом
      для i в [ii, ii+bs):
        для j в [jj, jj+bs):
          s = 0
          для l в [kk, kk+bs):  s += A[i][l] * Bt[j][l]
          C[i][j] += s
```
Плитки A та Bt розміром bs × bs (по 32 КБ при bs = 64) багаторазово перевикористовуються, поки лежать у кеші, тому кількість промахів різко зменшується. Складність та сама, O(n³), але константа значно менша. Розмір блоку підбирається експериментально (див. розділ «Вплив розміру блоку» у звіті): надто малий — великі накладні витрати циклів, надто великий — плитки не вміщуються в кеш.

Саме це ядро (`MmUtil.blocked`) виконується і в послідовній версії-еталоні, і в кожному листку дерева ПАРКС, тож порівняння послідовної та паралельної версій чесне: різниця лише в розподілі роботи.

## 3. Паралельний алгоритм у ПАРКС-Java

### 3.1 Декомпозиція

Матриця C ділиться на блоки C<sub>IJ</sub>. Воркеру, що відповідає за C<sub>IJ</sub>, потрібні лише:

* смуга рядків A<sub>I</sub> (ra × n);
* смуга стовпців B<sub>J</sub> (n × cb), що передається як рядки Bt.

Воркери **не обмінюються даними між собою** і не потребують синхронізації: кожен незалежно рахує свій блок C<sub>IJ</sub> = A<sub>I</sub> · B<sub>J</sub> блоковим ядром.

Для p воркерів сітка блоків gr × gc, де gr·gc = p, gr — найбільший дільник p, що не перевищує √p (`MmUtil.grid`): p = 1 → 1×1, 2 → 1×2, 4 → 2×2, 8 → 2×4. Межі смуг — `MmUtil.bounds` (різниця розмірів не більше 1, тому n не обов'язково ділиться на gr та gc).

### 3.2 Керуючий простір «Дерево»

Керуючий простір (КП) — дерево точок. Корінь — AM `MatMul` (у точці-ініціаторі), на кожному вузлі виконується AM `MmNode` (`point.execute("MmNode")`). Два режими (аргумент `flat|tree`):

| Режим | Структура | Як ділиться C | Повідомлень від кореня |
|---|---|---|---|
| `flat` | корінь → p листків (зірка) | сітка gr × gc, корінь напряму роздає смуги | p |
| `tree` | бінарне дерево з p = 2ᵏ листками | кожен вузол ділить свій блок навпіл уздовж **більшого** виміру | 2 |

Кількість точок: flat — p; tree — 2p − 2 (для p = 8: 2 + 4 + 8 = 14). Внутрішні вузли дерева лише розсилають смуги й збирають результат.

### 3.3 Протокол обміну (канал `info.parent`)

Батько надсилає дочірній точці:

```
int    levels   // скільки рівнів дерева лежить нижче цього вузла
int    n        // спільний розмір (кількість стовпців A = кількість рядків B)
int    ra, cb   // кількість рядків смуги A і кількість стовпців смуги B
int    bs       // розмір блоку для ядра
double[] a      // смуга A: ra*n елементів, рядками
double[] bt     // смуга Bt: cb*n елементів, рядками
```
Вузол відповідає одним повідомленням: `double[] c` (ra·cb елементів, рядками).

Вузол `MmNode`:
* якщо `levels > 0` і блок можна поділити — ділить його навпіл, створює 2 дочірні точки, передає їм відповідні половини смуг (при діленні за рядками A половинується, Bt передається цілою; при діленні за стовпцями навпаки), збирає відповіді та склеює C;
* інакше (листок) — виконує `MmUtil.blocked`.

Корінь збирає блоки C у повну матрицю (`System.arraycopy` по рядках).

### 3.4 Обсяг комунікації та масштабованість

Розмір даних вимірюється в кількості чисел double (8 байт).

* **flat**, сітка gr × gc: кожна смуга A передається gc воркерам, кожна смуга Bt — gr воркерам, плюс повертається n² елементів C. Разом ≈ (gc + gr + 1)·n². Для p = 1: 3n²; p = 4: 5n²; p = 8: 7n².
* **tree**: дані пересилаються на кожному рівні дерева (вузол повторно розсилає свої смуги далі), тому сумарний обсяг трафіку більший, ніж у flat; натомість корінь надсилає лише 2 повідомлення, і розсилання на різних гілках іде паралельно.

Нехай t<sub>f</sub> — час однієї арифметичної операції, t<sub>w</sub> — час передачі одного числа. Наближено:

  T<sub>flat</sub>(p) ≈ 2n³·t<sub>f</sub> / p + (gc + gr + 1)·n²·t<sub>w</sub> + накладні витрати запуску точок.

Обчислення зростають як n³, комунікація — як n². Отже **частка комунікації зменшується з ростом n** (відношення ~ 1/n), і для великих матриць очікується краще прискорення, ніж для малих; на малих n час передачі й серіалізації може перевищити виграш від паралелізму. Через те, що корінь передає дані послідовно і матриці A, B спочатку є лише на ньому, прискорення обмежене пропускною здатністю мережі й обчисленням на кореневій VM. Це теоретична оцінка; фактичні вимірювання — у `testing_report.md`.

### 3.5 Коректність і відтворюваність

* Елементи A та B — цілі числа 0..9 (зберігаються як `double`). Усі проміжні суми — цілі числа, що значно менші за 2⁵³, тому обчислюються **точно** і не залежать від порядку додавання. Тому результат паралельної версії має збігатися з послідовним **побітово**; корінь перевіряє це через `Arrays.equals` і друкує `correct=true/false`.
* Матриці генеруються за `seed` (`SplittableRandom`), тому експеримент відтворюваний.
* Локальна імітація (`sim/Check.java`) перевіряє 81 конфігурацію (n = 1, 2, 7, 64, 97, 130, 256; воркерів 1–8, flat і tree, різні bs) проти наївного множення.
